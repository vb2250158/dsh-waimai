# dsh-waimai

Alipay sign-in in payment settings displays the phone or SMS field requested by the current provider step and submits it through authenticated private RPC. An isolated backend browser runs the official page and its existing risk SDK. Each explicit input permits one corresponding request; SMS is never resent automatically and accepts the provider's four- or six-digit length. Submitted inputs are cleared from UI state and excluded from ordinary settings and logs. Additional human verification, registration, agreements and unfamiliar steps stop inline input and offer the official window.

Verification continues the selected account's valid pending order and existing Alipay H5 session; the backend rejects preparation or payment submission when no session exists. Sign-in before order creation is not supported, and verification material remains in the current plugin process. The backend rechecks the original order amount and SDK environment before connecting the verified session. Settings verification does not pay. The ordinary cashier connection in an order payment card can still call the platform payment submission API; it is distinct from settings-only verification.

Authenticated local clients can call the existing retail and payment tools through `retailSearch`, `retailCart`, `retailAdd`, `retailCheckout`, `paymentOptions` and `paymentPay` under `/waimai-login`, without model generation. These routes retain DSH session authentication, strict input validation, order ownership, quote expiry, spending limits and unknown-outcome safeguards. `paymentPay` rejects passwords and payment URLs; saved credentials are injected only by the Host. Requests carry an RPC request ID. After a timeout, query the original cart or order instead of resending. Live payment acceptance remains incomplete.

The original H5 entry initializes through `cashierMain`. Connecting an observed login, password or pre-confirmation subpage resumes through `refreshNoAuth` or `refresh` according to its current parameters. Unrecognized pages stop without guessing a recovery action. Payment cards distinguish provider rejection, sign-out, external verification, unsupported steps and result displays, separately indicating whether the backend submitted payment. Provider text and session parameters stay outside the UI and logs. Failed recovery preserves the original session and never resubmits payment; official order and payment queries remain authoritative.

The H5 backend payment branch under development initializes the original order's cashier through authenticated private RPC, keeps Alipay session data in memory, and submits one server-directed payment step without Agent Pay CLI. `paymentH5Start` accepts the account, order, confirmed amount and private session material; the destination always comes from that order's original payment response. `paymentH5Submit` accepts an ephemeral H5 reference and verification input. Neither endpoint is exposed to the model. Credentials, passwords and raw H5 responses stay out of conversations, ordinary settings and logs. The payment card connects the cashier, opens Alipay verification, connects the backend and submits one payment. Payment settings select the verification browser. The isolated verification window permits observed login and query APIs only; payment is submitted by the backend. Cookies and SDK environment data remain in the account process and are cleared at unload. After connection, the Agent can continue the same H5 session with `get_payment_options` and `pay_order`; password challenges use the saved payment credential or a one-time override in the private card. Live payment acceptance remains incomplete.

Payment settings save, replace and remove a six-digit Alipay payment password per Taobao account through authenticated private RPC and the public DSH credentials service. Passwords stay outside ordinary settings, model inputs/results and logs. The Host resolves the latest value per request and sends it only to the hidden H5 continuation, without a CLI fallback. Changed account identities reject previously saved passwords. Saving and removing credentials do not restart the plugin or modify payment records. The default local credential file is not OS-encrypted and cannot isolate processes running as the same OS user. Initial sign-in, SMS and additional provider verification still apply. See [0.8.27 migration](MIGRATION-0.8.27.md).

H5 submission shares the existing payment ledger and lock, persisting `h5Submitted: true` before sending. Timeouts and unknown responses require original-order reconciliation, never another submission. Additional agreements, card enrollment and unverified server actions stop backend submission. A success page does not establish payment; the original cashier or matching order's paid timestamp remains authoritative. See [0.8.26 migration](MIGRATION-0.8.26.md) for downgrade restrictions. Never restore an old ledger or remove deduplication records after a new payment attempt.

Cashier consultation and submission preserve the official entry's `payEntrance`, retaining `WAP` only when absent. When the official CLI is configured, original `ALIPAY_SDK` order strings pass through private process arguments without rebuilding signatures or treating the strings as browser URLs or query credentials. Official results still determine payment status; unknown outcomes cannot be retried. Synthetic tests cover this path; live Taobao background payment acceptance remains unverified.

When the CLI explicitly returns `PAYMENT_LINK_UNSUPPORTED`, the plugin retains the same order’s original official cashier URL in process memory for the payment card. It does not create another order, resubmit payment, or use that URL as an Agent Pay query credential. The URL is excluded from logs and sessions; after process restart, an unavailable link allows status checks only. Other failures and unknown results do not activate this path.

The adapter also parses CLI error receipts with `schemaVersion: 1.0`. `PAYMENT_LINK_UNSUPPORTED` appears on the conversation payment card without settling the official payment status or retrying. The current CLI/service has rejected a `maliprod.alipay.com` entry returned by Taobao in live testing; a saved configuration or successful connection check does not establish automatic payment support for these orders.

When the payment CLI returns no parseable JSON, raw stdout and stderr remain in memory behind authenticated private diagnostics, outside model tool results, persistent files and ordinary logs. Logs retain only execution classification, exit code and output byte counts. Timeout, spawn failure and nonzero exit do not establish payment status or authorize a retry.

Open Plugins → Takeaway assistant → Payment settings to configure the final per-order cap, daily budget, payment mode, quote lifetime and Alipay connection. Check connection runs only `--version` at the saved executable path; it does not query a wallet or submit payment. Save edits before checking. An available executable does not establish wallet authorization or payment success. Merchant whitelists have been removed; see the [0.8.20 upgrade guide](MIGRATION-0.8.20.md).

Optionally integrate the [official Alipay Agent Pay CLI](https://github.com/alipay/payment-skills) with `alipayAgentExecutable` (an absolute installed executable path) and `alipayAgentTimeoutMs`. An empty path retains the existing cashier flow. A DSH `pay_order` call privately hands the original provider material, confirmed amount and merchant to the CLI. The Host supplies session identity; model arguments cannot supply it. Verification uses the current official handoff, and unknown results permit queries only. Password and identity verification remain in the official Alipay flow. Follow official installation and eligibility requirements; live payment acceptance remains a separate verification step.

Payment records add optional `provider` and `agentQueryRef` fields. The latter retains only the query order number from this payment receipt. Signed links and full receipts remain in memory; full receipts are available only through authenticated private diagnostics. Existing records remain readable. After new fields have been written, downgrades must retain the current payment ledger and use a compatible reader; never restore an old ledger or remove newer payment records. When CLI output contains leading logs, only the terminal JSON command result with a numeric code or success/status fields is parsed; diagnostic records never supply payment references. Trailing non-JSON or incomplete output remains unknown. CLI return codes or messages never directly mark an order paid; reconciliation uses the original cashier result or matching official order payment time.

Alipay browser handoffs accept the existing cashier hosts and the exact HTTPS `mapi.alipay.com/gateway.do` and `openapi.alipay.com/gateway.do` endpoints documented in the [official WAP migration guide](https://developer.alibaba.com/docs/doc.htm?articleId=107095&docType=1&treeId=203). Signed query parameters are preserved. Diagnostics contain fixed destination rejection categories and the protocol and hostname, without complete addresses or query parameters. Without a configured official CLI, `ALIPAY_SDK` remains unknown instead of advertising an unavailable verification step. Opening verification does not establish payment success; the official result must still be queried.

Payment diagnostics record fixed result, action and handoff classifications plus protocol and hostname, never payment URLs, SDK payloads or extraMap contents. Unknown, paid and failed attempts hide generic payment links. Verification can resume only through the original handoff retained in memory; losing that handoff does not expose an automatic-payment order page or authorize another payment request. These changes do not resolve an existing unknown payment outcome.

After a payment attempt, the cart, checkout and payment cards no longer instruct users to continue payment in the official app. Unknown outcomes instruct users to check status. Missing original verification links explicitly instruct users to check the payment outcome and not pay again.

Payment status includes paymentQueryAvailable for a nonterminal payment with original cashier query parameters, or a configured official CLI and the current query order number or in-memory verification link. A false value after restart does not mean that the original payment was queried or that no charge occurred. Official order cancellation remains separate from an unknown payment result. Query parameters and verification destinations never enter the ledger.

Supermarket cashier consultation uses the official browser host, web container and WAP source without fabricating device fields. A missing payment timestamp in a pending order remains unconfirmed.

Restaurant POST_STANDARD creation responses unwrap the official payment envelope. Only eleme://cashier is normalized to the official HTTPS cashier. Unrecognized handoffs retain the created order IDs without implying payment success.

For Taobao orders, conversation-card refreshes and agent checkout retain their own unexpired quote references. A refresh does not replace another valid quote. Submission still checks account, address, cart, exact amount and expiry; a consumed quote cannot be submitted twice.

Each retry after an unknown Taobao creation result requires renewed explicit user authorization and official order reconciliation. retryOf must identify the latest unknown attempt for the same cart with no successor, and the amount cannot increase. Authorization never carries forward automatically; history and reservations remain intact.

Checkout, submission and adjustment send asac in URL query parameters as the official MTOP SDK does. The cashier unwraps official THIRD_PAY handoffs and reconciles terminal results through the payment query API. Query parameters remain in process memory; restarts preserve the payment ledger without retrying charges. These protocol fixes do not establish live order or payment acceptance.

Failure diagnostics also include fixed message-term categories such as address, tableware or coupon, without retaining remote text. Hints do not establish a failure cause or authorize a retry.

get_order_status can inspect an unknown creation attempt without invoking cashier methods that require an order ID. Only a created attempt with one order ID proceeds to payment reconciliation. An empty official match does not confirm absence. Submission diagnostics retain bounded numeric business codes and discard accompanying messages.

Taobao checkout and submission send the same Taobao channel header so coupons are priced for the intended channel. Taobao checkout and submission diagnostics share a quote reference and distinguish transport failures, platform responses and quote validation results. Logs retain structured protocol status and amounts without remote messages, order payloads, addresses or payment links. Live purchasing still requires verification with the current account.

Hema delivery store IDs are normalized before address checks, so reordered IDs do not invalidate checkout; changed store membership still stops submission. Order diagnostics retain structured return codes without remote messages, credentials or payment links. Unknown outcomes retain the original attempt and block duplicate submission.

## Agent ordering

Hema products open a specifications modal. get_product_details renders pack sizes, minimum quantity, quantity step, stock and pricing units. Recorded details require a fresh check. Refresh uses the recorded account and its currently selected address; changed identities, invalid references and failed refreshes discard old details. Plugin and conversation controls share SKU and quantity selection, pending feedback and a floating cart modal. Its item list scrolls within the modal so the title and close control remain visible. Success requires a matching SKU quantity delta with every unrelated line retained. Detail refresh and add re-read the original catalog page and store sale status. Closed sale periods and products missing from that page stop additions. Weighted and cross-platform products stop when their native add semantics are unconfirmed.

Agents read get_cart with platformId hema, then add_product_to_cart with productRef, skuId, integer quantity, revision and a stable operationRef. Native additions are sent once. The complete before snapshot and result remain in the private account file hema-cart-attempts.json. Timeouts and delayed readback require only cart reads; reload never resends. An unresolved attempt blocks new additions. Cart display prices do not establish membership discounts, delivery charges or the final amount due.

search_shops returns an opaque nextCursor for nearby merchant pages, including pages with no keyword matches. Positions are bound to the account, query, scope and native delivery selection; reloads, expiry or eviction require restarting from the first page. Advanced settings expose browseCursorSeconds and browseCursorLimit.

search_products reads current menus in up to ten explicitly selected stores. Results retain product names, pack descriptions, listed prices and availability, and declare selected-stores-only scope. Failed stores remain visible with complete: false. Explicit platform empty-store responses display their notice; unexplained or malformed responses remain errors. A case of water requires verification of bottle capacity, bottle count and the actual SKU; listed prices cannot establish the lowest checkout total.

Menu and preparation results use orderingAvailable for interactive ordering, automaticOrderingAvailable: false for disabled automated purchasing, and userConfirmationRequired: true for explicit confirmation.

The public tool.call.toolview slot renders shops, menu recommendations, carts, checkout confirmations and payment handoffs inside the conversation. show_order uses real menu itemIds and an optional budget. Users can choose variants, required extras and quantity, add items, remove one unit and request a quote inside the card. Plugin pages retain their floating cart; chat cards use an inline cart.

Agents can read get_cart and get_item_options, then change_cart with the current revision and validated selection references. Cart changes do not create orders. submit_order requires accountRef, shopId and maxAmount in yuan; it reads the real checkout total and returns a user confirmation card. The card refreshes the quote and checks the account, selected address, cart revision, expiry and budget before submitting. An explicit user confirmation can place a manual order while automation preview stays enabled. Scheduled purchasing remains disabled.

For an owned Taobao order, get_payment_options reads the official amount and selected payment method without charging. With explicit payment authorization, pay_order verifies the prepared reference, exact cents and spending cap, then submits one payment request. cashier-attempts.json reserves the attempt before sending; ambiguity, repeated confirmation and restarts never retry a charge. Only the selected Alipay method is supported; credit, account funding and new recurring authorizations are excluded. Verification handoffs stay in private authenticated UI RPC. get_payment_status reads official order state and, for supermarket orders, independently checks the payment timestamp, account and amount. Cancellation and payment are reported separately. URLs, provider parameters and credentials never enter model results or the payment ledger. Live payment acceptance remains pending.

## Installation and validation

Optional ingredient groups with zero allowance keep base variants available and disable extras. Zero is never interpreted as unlimited. Contradictory defaults, required extras or quantity rules stop the operation.

Install a fixed Git SHA through the managed DSH plugin installer. The package ships lib/ directly and has no build step. Run npm run check and npm test. Chinese documentation in README.md describes each configuration field, platform API and prior live validation. Migration guidance is in MIGRATION-0.3.0.md.

maxOrderAmount caps each order; dailyBudget caps daily reservations when nonzero. dryRun defaults to automation preview. loginDiagnostics records allowlisted login, cart and order stages without credentials or personal data. Existing local account and order files stay under DSH_HOME/waimai and never belong in environment sync.

Hema checkout resolves serviceable shop and location IDs through ShopDecideApi.decideByAddressId, then calls mtop.wdk.hema.cart.confirm and mtop.trade.order.build. Explicit lineIds and the current cart revision select quote items without changing official cart selections. Each selected product must currently have quantity one. The owner verifies address, SKU, quantity, listed subtotal, discount, shipping breakdown and consistent totals. Extra charges, additional agreements and ambiguous replies stop submission. The quote is shared by the plugin page and Agent confirmation cards.

Checkout selection is separate from phone selection. Only available lines with supported quantities enter the initial checkout selection; unsupported phone selections cannot block another product's quote. Hema delivery choices use mtop.trade.order.adjust for server repricing. A sole available option is selected and verified automatically; multiple choices appear in the plugin and conversation card. Changes replace the quote reference and clear amount confirmation. Missing selections, stale references and inconsistent totals prevent submission. Native delivery IDs and adjustment parameters stay in backend memory.

Confirmed Hema orders use one mtop.trade.order.create request after a shared lock, durable budget reservation and readback. Changed addresses or carts, expired quotes, exceeded limits and duplicates stop before creation. Unknown outcomes stay reserved and are never retried automatically. After checking the official app and confirming that the original request created no order, the user may explicitly authorize one retry from a fresh quote. The server binds it to the original unknown attempt, buyer, address and items, with no increase in amount. Reuse and retry chains are rejected; original records and reservations remain intact. Native parameters and signatures stay in backend memory; complete payment in the Hema app and verify official order status. Live delivery selection, checkout and shipping totals were verified on 2026-10-21. Real creation requests returned no recognizable order ID and the order API showed no matching new order; successful purchasing and payment remain unverified.
